# Decisions

Source of truth: `Support_Ticket_Tracker_Requirements_EN_v1.1.md`.

## D-001 Naming and the `com.berney` domain
The stack is TypeScript/Node.js (no JVM packages). `com.berney` is the organisation identifier and is applied to:
- npm scope: `@berney/support-ticket-tracker`
- OCI image vendor label and GHCR namespace `ghcr.io/berney/...`
- (if Java-style package folders are wanted later, move code under `src/com/berney/...`; not done by default)

## D-002 Pinned versions (stage 1, verified 2026-10-10)
Node 22.23, TypeScript 7.0.2, `adminjs` 7.8.17, `@adminjs/express` 6.1.1, `@adminjs/prisma` 5.0.4,
`prisma` / `@prisma/client` 6.19.3, `express` 4.21.2, `express-session` 1.18.1, PostgreSQL 17.

- **Prisma stays on 6.x.** `@adminjs/prisma@5.0.4` declares peer `@prisma/client ^5 || ^6`; Prisma 7/8 are not supported. Do not upgrade Prisma until the adapter does.
- **Express stays on 4.x.** The AdminJS plugin does not declare Express 5 support.
- `multiSchema` is GA in Prisma 6; no preview flag.

## D-003 Every referenced model must be registered in AdminJS
`list`/`show` of Ticket fail with "no resources with given id" unless User, Agent, Customer, SupportGroup, TicketStatus are registered. Register all, then hide/restrict via `isVisible`, `navigation: false` and action `isAccessible` (stages 3-6). Registration is not exposure.

## D-004 Local development database
No Docker on the dev machine, so `npm run dev:db` starts PostgreSQL via `embedded-postgres` (beta tag, dev-only, port 15432, UTF8 with ICU locale `en-US`, data in `.devdb/`). The ICU locale matters: with locale `C`, `ILIKE` is not case-insensitive for Cyrillic. If `.devdb/` was created earlier with `--locale=C`, delete it and run `npm run dev:db`, then `npx prisma migrate deploy` and `npm run seed:reference`. Port 54329 is in a Windows reserved range; avoid 54198-54397.

## D-005 AdminJS bundling at startup
AdminJS bundles custom components only when `NODE_ENV=production` (the Docker image sets it), into `.adminjs/` at startup (~30-60 s here). The bundle is cached: after adding or changing a component delete `.adminjs/` or the browser reports "Component ... has not been bundled". A fresh Docker build starts clean. The container's runtime user needs write access to it. Healthcheck/readiness must tolerate the delay.

## D-006 One session, own login controller (stage 3)
`@adminjs/express` `buildRouter` reads `req.session.adminUser` as `currentAdmin`, so the app uses its own `express-session` + `connect-pg-simple` (table `support."Session"`, owned by Prisma) and `buildRouter`, not `buildAuthenticatedRouter` (which would create a second session). `requireUser` reloads the user from the DB on every request and checks `isActive`, an active Agent profile for AGENT, `sessionVersion`, and the 8 h absolute lifetime; idle timeout (30 min) is the sliding cookie/store expiry (`rolling`).

Middleware order (matters): health -> session -> `/auth` form parser (4 KiB) -> CSRF -> `/auth` routes -> `requireUser` -> AdminJS router. `buildRouter` brings `express-formidable`, which writes uploads to disk, so CSRF must run before it and uploads (stage 8) need their own route mounted before the AdminJS router.

## D-007 CSRF
Synchronizer token in the session + mandatory `Origin` check (missing Origin is rejected on unsafe methods). Token is read from `X-CSRF-Token` or a parsed `_csrf` form field. The AdminJS client gets the header from `public/csrf-client.js` (patches XHR and fetch, same-origin only, token from `GET /auth/csrf`). Logout is POST; the link AdminJS renders (GET) shows a confirmation form.

## D-008 Known limitations
- Login rate limits are in-memory: correct for a single replica only; multiple replicas need a shared store.
- Argon2id parameters: m=19456 KiB, t=2, p=1 (OWASP minimum); revisit against the production host's CPU.
- The model/resource exposure in AdminJS is still unrestricted for any signed-in user; RBAC is stages 4-6.

## D-009 Domain services and policies (stage 4)
- `TicketService` (create, update, assign, changeStatus, get), `GroupService`, `AgentService` take an `Actor` (`userId`, `role`, `agentId`) and load the group scope inside their own transaction. Callers (AdminJS actions, stage 5) must go through them; standard AdminJS new/edit/delete must be disabled or replaced.
- Every write is one transaction: ticket change + `version` increment + `TicketHistory` row. Concurrent writers are serialized by `UPDATE ... WHERE id AND version`; the loser gets `version_conflict` (409).
- Out-of-scope and unknown ids give 404 (`not_found`); in-scope but insufficient role gives 403 (`admin_only`, `group_not_allowed`).
- Row locks (`FOR SHARE` on assign, `FOR UPDATE` on deactivate/remove-member, always group before agent) prevent an active ticket ending up on an inactive agent when assignment and deactivation race. Covered by a repeated race test.
- `changeStatusInTx` is the unit reused by the all-or-nothing bulk action (stage 9).
- Reopening takes an optional `groupId`/`assignedAgentId` in the same call, so the transition and the new assignee are atomic.

### Interpretations of the requirements (confirm or change)
- Ordinary edit covers subject, description and priority (the matrix says "description/priority"; subject added so typos can be fixed).
- On a group change the assignee is never cleared implicitly: keeping an assignee who is not in the new group fails; to unassign (NEW only) pass `assignedAgentId: null`.
- Changing status requires being in the ticket's group scope, not being its assignee.
- "Active assignee" for NEW/WAITING -> IN_PROGRESS, UNRESOLVED and every reopening means: active agent, member of the active group. WAITING_CUSTOMER and RESOLVED only require an assignee to be set; CLOSED requires none.
- An agent whose *User* is deactivated is not rejected as an assignee yet (User deactivation must also deactivate the Agent; stage 6).

## D-010 AdminJS resources are guarded (stage 5)
`GuardedResource` (`src/admin/guarded-resource.ts`) replaces the stock Prisma resource. AdminJS passes the action context to `find/count/findOne/findMany/create/update/delete`, so every data access knows the actor:
- Reads: mandatory scope AND-ed with user filters (Ticket: group scope; Group/Agent/User/Status: see `resources/reference.ts`). Custom filter conversion: case-insensitive `contains`, `__none__` on references means unassigned, malformed values match nothing instead of raising a database error. Page size is clamped to 100; `id` is a sort tie-breaker.
- Writes: only through `TicketService` / `CustomerService`; a resource without a write handler is read-only; `delete` always refuses. Generic delete and bulk delete are also marked inaccessible.
- Fields: `User.passwordHash`/`sessionVersion` are removed from every row for every actor; an AGENT receives only `displayName` of users.

AdminJS behaviours that shaped this (all covered by tests):
- `isAdapterFor` sees `model` + `client` on a resource instance and silently replaces it with the stock `Resource`. `GuardedResource` clears `client` after construction; removing that line disables every guard.
- A record counts as saved unless a *property* error exists. Errors without a field (version conflict) are attached to `fallbackErrorField` (`version` / `name`), otherwise the UI says "successfully updated" while nothing was saved.
- Refusals (not found, forbidden) come back as HTTP 200 with `record.baseError.type`; clients and tests must look at that, not at the status. Errors thrown as `DomainError` outside that path (e.g. creating in a foreign group) keep their HTTP status via the app error handler.
- `new` and `edit` share one visibility key (`edit`). `ReadOnlyWhenEditing` renders the stock select when creating and read-only text when editing. `version` is not a form field; it travels in the record params and is sent back on save.

Customers: any staff member creates; only ADMIN edits/deactivates (the `edit` action is hidden for AGENT and `CustomerService` refuses too). Customers are never deleted.

## D-011 Ticket actions, read models and custom components (stage 5b)
- **Actions.** `changeStatus` and `assignTicket` are AdminJS record actions with React forms (`ChangeStatusForm`, `AssignForm`); they POST to `TicketService`. Hidden record actions `formState`, `history` (Ticket) and `customerTickets` (Customer) return JSON for the components. The data comes from `TicketQueries`, which applies the same scope as the list: out-of-scope tickets behave as if absent.
- **AdminJS contract.** A record action must return `{ record }` (RecordJSON) or it throws `ConfigurationError`; our data rides along next to it. Unlike the built-in actions, our mutation actions answer with real HTTP statuses (`422` + `details`, `409`, `403`) so the forms can show field errors. When AdminJS cannot load the record at all (outside the scope) it answers HTTP 200 with a `NotFoundError` base error before our handler runs.
- **The forms only offer what the server will accept** (`formState` lists the transitions allowed for this actor and status, and the active members of the selected group), but the service re-validates everything.
- **Saved filters.** The dashboard shows live counts and links to ticket-list URLs: "My tickets" (`filters.assignedAgent=<agentId>`), "Unassigned" (`filters.assignedAgent=__none__`), "Waiting for customer" and "Unresolved" (`filters.status=<id>`). Counts and lists share one scope, so they always agree.
- **History** is read-only, newest first, 20 per page, with ids resolved to names. **Age** is computed on read (`age.ts`), never stored.
- **Labels and help text** come from `field-catalog.ts`. AdminJS `PropertyOptions` has no `label`: labels are generated as locale translations (`catalogTranslations()`), help text goes in `description`.
- **Components load from `dist/`** when it exists (they import each other with `.js` specifiers). For `npm run dev` run `npm run build` once, or `npm run build:watch` alongside, and delete `.adminjs/` after changing a component (D-005).
- **UI language is English** (requirements are English; UNRESOLVED is "Unresolved" there). A Russian UI would be a locale in `field-catalog.ts` plus translations of the component strings. Open question for the product owner.

## D-012 Staff, groups and statuses (stage 6)
All writes go through `UserService`, `AgentService`, `GroupService` and `StatusService`, which are ADMIN-only; the AdminJS forms only expose what may be edited.

**Accounts**
- Role and password never travel through the profile form: `UserService.update` accepts only name, email and active state (strict schema), and the form rejects a changed role or a password with a pointer to the right action. Roles change with **Change role**, passwords with **Set password**.
- Role change, password change and activation/deactivation bump `sessionVersion`, so the person is signed out on the next request (tested end to end over HTTP).
- Nobody changes their own role or deactivates themselves (no self-escalation, no self-lockout). The last active ADMIN can be neither demoted nor deactivated; the check runs under `SELECT ... FOR UPDATE` on all active admins, because without the lock two admins demoting each other at once both succeed and leave none (the test repeats the race 12 times and fails without the lock).
- An AGENT always has an active support profile (created with the account or on demotion). Deactivating the account deactivates the profile, which is refused while it holds active tickets; reactivating an AGENT account reactivates the profile. A rename propagates to the profile name. An ADMIN gets a profile through the Agent resource ("create profile"), which is what makes them assignable.
- A profile cannot be switched off on its own if it belongs to an AGENT account (an AGENT must always have an active profile, requirements section 5: deactivate the account instead, which also signs the person out) or to the caller (no self-lockout through the Agent resource). That leaves ADMIN accounts that work tickets and stop doing so. Found by code review of stage 6.
- Passwords: 12-256 characters, length only (no composition rules), Argon2id. There is no self-service password change yet.
- Created and updated rows are redacted like reads, so a new account never echoes its hash.

**Groups**: the code is immutable and validated (`[A-Z][A-Z0-9_]{1,39}`); deactivation is refused while the group has active tickets; only active agents join active groups; removing a member is refused while they hold active tickets in the group. An AGENT can read the member list of their own group (names only); ADMIN gets add/remove and the candidate list.

**Statuses**: only name, color, order and active flag change; the code is fixed. NEW can never be deactivated and a status that tickets use cannot be. A deactivated status is no longer offered by the forms and is refused as a transition target (`FOR SHARE` on the target, `FOR UPDATE` on deactivation, same pattern as agents). New statuses need a migration and workflow tests; the resource has no "create".

**Forms**: `ModeField` (formerly ReadOnlyWhenEditing) renders per mode from `property.custom.mode`: read-only on edit, create-only, or edit-only, because AdminJS shares one visibility key between new and edit.

**Testing note**: the last-admin tests switch other active admins off for the duration of the test and always restore them. Run integration tests against a throwaway database, not one with real accounts.

## D-013 Shared guards
`requireAdmin(actor)` lives in `src/policies/ticket-policy.ts` and is the only way services refuse non-administrators; `isUniqueViolation` (P2002) and `isRecordNotFound` (P2025) live in `src/domain/db.ts`. Do not copy them into services.

## D-014 Comments inline (stage 7)
- **No Comment resource in AdminJS.** Comments exist only inside the ticket page: `listComments` (data), `addComment` and `editComment` (POST) are Ticket record actions backed by `CommentService` / `CommentQueries`. The ticket id is the record being viewed and the author is the session user; the payload may carry only `body` (and, for edits, `commentId` and `version`). An edit also names the ticket from the URL, and the comment must belong to it.
- **Rules** (`policies/comment-policy.ts`, pure and unit-tested): anyone who can see the ticket may comment; ADMIN edits any comment, an AGENT only their own; nobody adds or edits on CLOSED or UNRESOLVED tickets (reading stays); RESOLVED stays open for both. Unknown status codes fail closed. There is no delete. Whether the ticket's group is active does not matter for comments (the spec ties that only to ticket edits).
- **Locking.** Adding takes `SELECT ... FOR UPDATE` on the ticket row, editing `FOR SHARE`, then reads the status. A status change updates the same row, so a comment cannot slip onto a ticket being closed (a deterministic test holds an uncommitted close and shows the add waiting, then refusing). The lock reads one table only: a JOIN inside a locking read drops the row when a concurrent update commits while waiting (found by that test).
- **Activity.** A new comment bumps the ticket's `updatedAt` (so it rises in the default list order) but not its `version`, so someone's open ticket edit does not become stale because of a comment. Edits do not touch the ticket.
- **Edit conflicts** use the comment's own `version` (409). Text is trimmed, 1-5000 characters, stored as typed and rendered as a text node by the component (markup is shown, never executed).
- **UI.** `CommentsInline` is a virtual property on the ticket show and edit pages: 10 comments per page, oldest first, jumping to the page of a new comment, in-place edit, "edited" mark, frozen tickets show a message and no controls. On the "new" form it says comments are available once the ticket exists. Its buttons are `type="button"` because on the edit page it sits inside the ticket's own form. Attachments join it in stage 8.

## D-015 Attachments and object storage (stage 8)
- **Storage behind an interface** (`src/storage/storage.ts`): `S3Storage` (Supabase Storage through its S3 API, path-style, the SDK's own presigner) and `MemoryStorage` (tests and development). `createStorage(env)` picks S3 when all four `S3_*` variables are set, otherwise memory. `loadEnv` refuses a production or demo environment without S3, and a partial configuration anywhere, so uploads never silently go to memory. Nothing is ever written to the server's disk.
- **Verified**: `S3Storage` is unit-tested with a replaced HTTP transport (request method, path-style URL, headers, a 60-second presigned URL with the attachment disposition and no secret in it). It was also checked against a real **private** Supabase bucket with `npm run storage:check` (write, head, list, presign, delete for PNG, JPEG and PDF) and by downloading through a presigned URL (200, `Content-Disposition: attachment`, identical bytes; the same URL without its signature gives 403). The bucket's own allowed-MIME setting must include `image/png`, `image/jpeg`, `application/pdf` and `text/plain` and its file size limit must be at least 10 MiB; otherwise `text/plain` is refused by the provider (`storage:check` names the refused types). The endpoint is `https://<project-ref>.supabase.co/storage/v1/s3`; newer projects show `https://<project-ref>.storage.supabase.co/storage/v1/s3`, which works the same.
- **File size limit is 10 MiB** (changed from 5 MiB at the owner's request; requirements section 10 was updated to match). The limits live in `src/storage/limits.ts` (pure constants, also used by the admin components): `MAX_FILE_BYTES`, `MAX_ATTACHMENTS_PER_COMMENT`, the allowed extensions and the label `FILE_LIMIT_LABEL`; validation, multer, the Content-Length precheck, every message and the browser pre-check derive from them. Upload memory is bounded by `MAX_CONCURRENT_UPLOADS` x 10 MiB (default 40 MiB).
- **Upload path**: `POST /internal/comments/:id/attachments`, mounted after session, CSRF and authentication and before AdminJS (whose parser writes uploads to disk). multer with memory storage and hard limits (one file, 10 MiB, no other fields); the Content-Length header is checked before the body is read; at most `MAX_CONCURRENT_UPLOADS` (default 4) run at once (429 otherwise), so memory is bounded by 4 x 10 MiB.
- **Validation** (`file-validation.ts`): PNG, JPEG, PDF, UTF-8 text. The type is decided from the bytes; extension, declared content type and content must agree. SVG, HTML/XML (also under a .txt name), executables and archives are rejected. Text must be valid UTF-8 without control characters. The client name is sanitized metadata; the object key is `tickets/{ticketId}/comments/{commentId}/{uuid}`, chosen by the server. This is not antivirus.
- **State machine**: upload = reserve a PENDING row (ticket lock, then comment lock, limit of five counts PENDING and READY) -> put -> READY, re-checking that the ticket is still open (a ticket closed during a long upload discards the file); failure = FAILED plus best-effort delete and a generic 502 (provider messages can contain endpoints and keys). Delete = DELETING -> delete object -> remove row; repeating it finishes a half-done deletion. Who may upload or delete is exactly who may edit the comment.
- **Download**: `GET /internal/attachments/:id/download` checks ticket scope and READY state, then redirects (302, no-store, no-referrer) to a 60-second presigned URL with `Content-Disposition: attachment`. Known limit: the URL stays valid until it expires even if the user's access is revoked meanwhile.
- **`npm run storage:reconcile [-- --dry-run] [--older-than-minutes N]`**: stale PENDING (> 1 h) -> object deleted and row FAILED; stale FAILED -> object and row removed (in a later run than the conversion); stale DELETING -> finished; objects without a row (older than the cutoff) -> deleted; READY rows whose object is gone -> reported only. Younger items may be in flight and are left alone. Meant to run on a schedule (stage 11). **Age is measured from `Attachment.stateChangedAt`** (set on every state change), not from `createdAt`: a long-lived file that a user has only just started to delete is not mistaken for an abandoned operation, and a PENDING row converted to FAILED waits a full cutoff before its row is removed.
- **Refusals discard the unread body at the moment of refusal** (`discardBody`, called by the CSRF and authentication refusals, the size and load limits and the error handler), before the response is built. Draining only at `res.end` was too late (tested). In a real Chrome a 6 MB upload gets a clean 413 JSON and a large body without a CSRF header or session a clean 403 JSON; the `ECONNRESET` seen with supertest's per-request servers is a test-client artifact, so those cases are covered by unit tests that assert the drain.

## D-016 Bulk status change (stage 9)

- **One transaction, every ticket through the single-ticket rules.** `TicketService.bulkChangeStatus` calls `changeStatusInTx` for each ticket, so scope, version, workflow, outcome fields, ADMIN-only transitions, status activity and history are exactly those of a single change. A refusal of any ticket rolls the whole transaction back (`BulkRejectedError`, HTTP 409, code `bulk_rejected`).
- **The whole batch is tried before the verdict**, so the operator sees every refused ticket at once, not only the first. The error carries `failures` (ticket id, number, code, message); `details` maps `Ticket #<number>` to the reason for the form. Ids that are unknown or outside the actor's scope are reported by id with the same message (`not_found`) and without a number, so existence is not disclosed.
- **Input**: at most 100 id/version pairs (`BULK_MAX_TICKETS`; duplicates are merged first and the distinct tickets are counted, before the database is touched: `batch_too_large`, 422), a target status, `reason`, and `resolution` or `unresolvedReason` as the target requires. Duplicate ids are merged when the version is the same and rejected when it differs. Strict schema: no `groupId` or `assignedAgentId` (bulk never reassigns), so a transition that needs an assignee fails for tickets that have none.
- **The size is also checked ahead of AdminJS.** AdminJS loads every id of `?recordIds=` before any handler runs, so `limitBulkSelection` (`src/http/bulk-limits.ts`, mounted in front of the AdminJS router) applies the same limit to the query on GET and POST and rejects a `recordIds` that is not a single comma-separated list.
- **`reason`** is required exactly where the workflow table requires it (for example reopening or waiting for the customer) and optional otherwise; the form marks it accordingly. It is not mandatory for every transition because the single-ticket action has the same rule.
- **UNRESOLVED needs `confirmSharedReason: true`**: the one reason is saved on every selected ticket and the operator must say it fits all of them (checked by the service, and the form keeps the button disabled until the box is ticked).
- **Deadlocks**: tickets are processed in ascending id order, so two overlapping batches take their row locks in the same order and one of them fails cleanly on the version check instead of deadlocking. Transaction timeout 30 s. The status ids and the lock on the target status are read once for the whole batch instead of once per ticket (`BulkPrepared`), which removes two of about eight round trips per ticket; a remote database still needs more time than a local one, so the 100-ticket test only guards the local case.
- **AdminJS wiring**: a bulk action `bulkChangeStatus` on Ticket, available to ADMIN and AGENT (the service enforces scope and roles). `GET .../bulk/bulkChangeStatus?recordIds=...` returns the records AdminJS needs plus `tickets` (with current versions), `unavailable` (selected ids that are out of scope, counted but not named) and `targets` (only the changes valid for every selected status, ADMIN-only ones only for an admin). The form shows which selected tickets have no assignee and warns when the chosen change needs one (a bulk change never assigns, so those tickets would be refused). The form POSTs the id/version pairs it displayed and, on success, lists the changed tickets (`#n`) with a link back to the list; the `recordIds` query is not trusted on POST. `bulkDelete` stays off.
- **AdminJS's own NotFoundError** (a selection in which no id can be loaded) is mapped to 404 `not_found` by the error handler instead of 500.
- **Concurrent edits (optimistic locking).** Opening a ticket locks nothing. Every ticket has a `version` that grows by one on each change, and the bulk form sends back the version of every ticket it displayed. Each ticket is written with `UPDATE ... WHERE id = ? AND version = ?`, so a ticket that someone else saved after the form was opened matches no row and is refused as `version_conflict`. What happens in the usual races:
  - *Someone saved a selected ticket before the batch:* the whole batch is refused, every conflicting ticket is named, nothing changes. The operator reloads the list and repeats.
  - *Someone saves one of the tickets after the batch:* their request carries the old version and gets the same 409, so a bulk change is never overwritten silently.
  - *Both write at the same moment:* the `UPDATE` takes the row lock, the second writer waits for the first commit and then fails the version check. No lost update is possible.
  - *Two overlapping batches:* row locks are taken in the same (ascending id) order, so there is no deadlock; one batch succeeds and the other is refused on the version check.
  - *Known limits:* one busy ticket blocks the whole batch (all-or-nothing is the requirement); a new comment does not change `version` (D-014), so a comment added after the form was opened does not block a bulk status change; there is no merging of changes, a human resolves the conflict.
- **Not promised**: an atomic operation for 500 tickets (use batches of at most 100) or a background job with progress.

## D-017 Demo dataset (stage 10)

- **Ownership by deterministic ids, no registry table.** Every row of the dataset has a name-based UUID (version 5) of the dataset name, the kind of record and its position (`seedId`, `src/seed/ids.ts`). The ids never depend on the random seed, so `seed:reset` and `seed:verify` know the owned rows without storing anything: users, agents, groups, customers and tickets by their ids; comments, history and attachments through their ticket. Reset never truncates a table, drops a schema or lists the bucket.
- **Reproducible content.** A fixed pseudorandom generator (mulberry32, `--seed`, default 42) with one forked stream per part of the dataset, so changing one part does not reshuffle the others. Dates are relative to the reference date (default: now), tickets are created within the previous 90 days. The default dataset's tickets are numbered 1001, 1002, ... in order (`TICKET_NUMBER_BASE`); after a reset the numbers are the same, and the sequence is moved past them (and back to 1 after `--delete-only` when no ticket is left). Other datasets (tests) use the database sequence.
- **Volumes and shapes follow section 13 exactly**: 2 ADMIN without Agent, 15 AGENT, 5 groups, 25 memberships (ten agents in two groups), 300 customers (some without phone or company, similar names, Cyrillic), 2000 tickets with the exact status counts, 10000 comments (0-20 per ticket), 200 attachments. Every ticket's history is a chain of transitions from the workflow table (`findTransition`), written with the same snapshot function as `TicketService` (`ticketSnapshot`), ends in the ticket's current state and uses `applyOutcome` for the outcome fields; CLOSED passes through RESOLVED, UNRESOLVED through IN_PROGRESS or WAITING_CUSTOMER, ADMIN-only steps are done by an admin, and some tickets were reopened from UNRESOLVED and then resolved (the checker demands at least one). Comments are placed only in the periods in which the ticket was not CLOSED or UNRESOLVED, and `updatedAt` is the latest of everything that happened.
- **One checker for two uses.** `checkDataset` (`src/seed/checks.ts`) verifies counts, memberships, assignees (non-NEW tickets are assigned to an active member of the group, NEW includes unassigned ones), the history chain, dates, comment placement and the awkward cases (long subjects, Cyrillic, multiple comment pages, similar names). It also demands that every priority is used, that tickets lie within the 90 days before the reference date (estimated from the newest update when it reads the database), that every address is on `example.test`, that assigned agents are active, that every resolving or unresolving step carries its date, and that attachments are dated between their comment and the ticket's last update. The unit test runs it on the generated dataset and corrupts the data to see it complain; `seed:verify` runs it on the rows read from the database and adds a Storage `head` for every attachment (present and the same size).
- **Idempotent.** Records are inserted with `createMany(skipDuplicates)` by their fixed ids: a rerun adds nothing twice and fills in what is missing, including files that have vanished from Storage. Existing rows are not updated; to regenerate with another seed or reference date, reset first (a rerun with another seed over an existing dataset keeps the old content and does not warn). Before anything is written, a clash with rows that are not the dataset's (a foreign account with a demo e-mail, a ticket on a demo number) stops the run.
- **Files are real.** Small valid PNG, baseline JPEG (flat 8x8 blocks, a custom Huffman table), one-page PDF with correct xref offsets and UTF-8 text are generated in code (no binary fixtures in the repository), checked with the same `validateUpload` as user uploads and put through the normal storage service before their rows are inserted. `seed:demo`, `seed:verify` and `seed:reset` refuse the in-memory storage, because rows pointing at files that vanish with the process would be fictitious.
- **Passwords** come from `SEED_ADMIN_PASSWORD` and `SEED_AGENT_PASSWORD` (12+ characters), one Argon2 hash per account. Existing accounts keep their password unless `--rotate-demo-passwords` is given, which also ends their sessions. There is no default password anywhere.
- **Guards.** Seeding is refused outside development and demo (an unset `APP_ENV` means development, as in the application). Reset needs `APP_ENV=development|demo` set explicitly (an unset variable is refused), `ALLOW_DEMO_RESET=true` and `--dataset` and `--confirm` equal to the dataset name; production is always refused. Reset deletes the database rows in one transaction (so anything else that still refers to the demo data, such as a ticket created by a reviewer in a demo group, makes it delete nothing and say so), then the files by their keys (leftovers are removed by `storage:reconcile`), then recreates the dataset. It checks the passwords it will need before deleting anything. The counts are printed before anything is deleted (`--dry-run` stops there) and `--delete-only` skips the recreation. The files of attachment rows in any state (READY, PENDING, FAILED, DELETING) are deleted with the rows.
